# AI による分類・概要の生成 計画(標本検証の段階)

蔵書の本ごとに、Claude のモデルの知識と Web 検索から「形態・主題・短い概要」を生成し、SQL で絞り込み・集計できるようにする案。NDL サーチの書誌情報では、マンガ(蔵書の約 73%)にほとんど件名が付かず、意味分類の手がかりが足りなかったことが動機。

**現在は標本検証の段階。kindb 本体(スキーマ、CLI、不変条件)はまだ変えない。** 標本で精度とコストを測り、全量を回す価値があると分かってから、取り込み先を `docs/spec.md` に設計する。語の意味は `docs/glossary.md` に従う。

## 方針

- **NDL の書誌情報とは別系統で扱う。** `bib_*` は「誤った書誌情報を付けるより何も付けない」を不変条件にしている。モデルの推定はこれと両立しないので、将来テーブルを作るときも `bib_*` に混ぜず、`basis`(根拠)、`confidence`、モデル名、生成日を持たせる。`v_books` の既存の列にも混ぜない。
- **入力は書名、著者、Kindle ジャンル、シリーズ名。** NDL の照合結果(ISBN、NDC の分類名、件名、出版社)は、あれば補助に渡す。照合に成功した本だけを対象にしない。成功しなかった本が、補いたい層に当たるため。
- **ISBN は Web 検索の段階で作品を特定する手がかりとして使う。** モデルが知識から ISBN を逆引きすることは期待しない。標本では ISBN を入れた場合と外した場合(`export --no-isbn`)を比べ、差が小さければ ISBN を使わない構成にする。
- **作品単位で処理する。** `series_asin` があればシリーズを 1 作品とし、なければ単巻を 1 作品とする。代表の 1 冊は巻数の若い順。
- **分類は固定の語彙を主にする。** 自由記述だけでは集計できない。形態は 1 つ、主題は最大 3 つを固定語彙から選び、自由タグは補助とする。語彙は `scripts/annotation_trial.py` の `FORMS` / `TOPICS` が正で、標本で不足や紛らわしさが見つかったら直す。
- **概要は自分の言葉で 100 字以内。** Web で見つけた紹介文は写さない。
- **「分からない」を許す。** `basis` が `unknown` のときは分類も概要も空にする。知らない作品を推測で埋めることが、いちばん避けたい失敗。

## 実行の構成

1. **一次分類(Haiku)。** 知識だけで分類し、`basis` と `confidence` を返す。
2. **補完(Sonnet + Web 検索)。** 一次で `unknown` か `confidence` が `low` だった作品だけを回す。全作品を Web 検索に回さないことが、コストの主な節約になる。
3. 実行は kindb の外(Claude Code のサブエージェント、または API の Batch)で行う。kindb は「入力を書き出す」「結果を取り込む」だけを担当する(取り込みは検証の後で設計する)。

この構成は仮説で、標本で次を測ってから決める。

- Haiku は日本のニッチなマンガ・ラノベで、知らないのに分類を返さないか(`known` と自己申告した作品の正解率)。
- `confidence` の自己申告は、実際の正解率と対応するか。
- Web 検索は、一次の `unknown` / `low` をどれだけ救うか。1 作品あたりのトークン数と時間。

## 標本検証の手順

補助スクリプトは `scripts/annotation_trial.py`。DB は読み取り専用で開く。**実際の蔵書 DB を使う場合も、`--db` に一時コピーを指定する**(CLAUDE.md の実行時の注意に従う)。

1. **標本を作る。** 層(ジャンルの推定 × ISBN の有無)ごとに同数を取る。シードが同じなら同じ標本になる。

   ```bash
   uv run python scripts/annotation_trial.py export --db <一時DB> --out sample.jsonl --per-stratum 12
   uv run python scripts/annotation_trial.py export --db <一時DB> --out sample_noisbn.jsonl --per-stratum 12 --no-isbn
   ```

   ジャンルの推定は粗い。`コミック・ラノベ・BL` を持てば `manga`、ジャンルが空で NDC もなければ `unclear`、それ以外は `other`。`unclear` にマンガと一般書が混ざる。

2. **システムプロンプトを作る。** `uv run python scripts/annotation_trial.py prompt > system_prompt.txt`

3. **条件ごとに生成する。** 同じ入力と同じプロンプトで、次を比べる。結果は 1 行 1 作品の JSON Lines。
   - Haiku(知識だけ)
   - Sonnet(知識だけ)
   - Sonnet + Web 検索(ISBN あり / なし)
   - 各条件のトークン数と所要時間を記録する。

4. **形式を検証する。** 語彙外の値、`unknown` の矛盾、概要の長さ超過、`web` なのに出典がない行を検出する。分布も出る。

   ```bash
   uv run python scripts/annotation_trial.py check results_haiku.jsonl --sample sample.jsonl --sheet score_haiku.csv
   ```

5. **目視で採点する。** 採点表の `form_ok` / `topics_ok` / `summary_ok` に 1 / 0 を入れる。判定は 1 人の目視で、標本が小さいので、精度は目安として扱う(NDL の標本測定と同じ)。

6. **判断する。** 条件ごとの正解率、`confidence` 別の正解率、1 作品あたりのコストを並べ、全量を回すか、段階の切り方を変えるかを決める。

## 全量に進む場合に決めること(未設計)

- 取り込み先のテーブル、`v_books` へ出すか別ビューにするか。
- 不変条件への影響。`bib_*` を書くのは `enrich` と `rematch` だけ、という規則とは別に、新しい書き手を置く。import 系が触らないテーブルとして扱う。
- `SKILL.md` に、推定値として扱う規則(出力するときに「AI 推定」と明示する)を書く。
- 再生成の単位(モデルを変えたとき、語彙を変えたとき)と、手動訂正の持ち方。

## 対象外

- Web で取得した紹介文の保存。取得元の規約を確認できないため。
- NDL サーチ以外の書誌 API の追加。
